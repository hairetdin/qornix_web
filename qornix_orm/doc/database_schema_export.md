# Database schema export

`DatabaseSchemaExporter` bridges technical database introspection and the semantic schema model used by the schema-driven pipeline.

It converts:

```text
DatabaseSnapshot
  -> SchemaDocument current
  -> canonical XML compatible with qornix_orm/schema/schema_app.xsd
```

## Why this layer exists

The schema pipeline must not compare raw user XML directly with raw database introspection rows.

The desired model comes from user XML:

```text
user XML
  -> XSD validation
  -> SchemaDocument desired
  -> normalization
```

The current model comes from the database:

```text
database
  -> DatabaseIntrospector
  -> DatabaseSnapshot
  -> DatabaseSchemaExporter
  -> SchemaDocument current
  -> canonical XML
  -> normalization
```

Future diff code should compare:

```text
SchemaDocument desired
SchemaDocument current
```

not:

```text
raw XML
raw database snapshot
```

## Public API

```cpp
#include "core/database_schema_exporter.h"

DatabaseSnapshot snapshot = ...;

DatabaseSchemaExportOptions options;
options.applicationName = "ShopSchema";
options.applicationVersion = "1.0";
options.description = "Schema exported from production database";

auto result = DatabaseSchemaExporter::exportSnapshot(snapshot, options);

if (!result.ok()) {
    // inspect result.errors
}

const SchemaDocument& current = *result.document;
std::string xml = current.toCanonicalXml();
```

## Export options

```cpp
struct DatabaseSchemaExportOptions {
    std::string applicationName;
    std::string applicationVersion = "1.0";
    std::string description;
    std::string schemaFormatVersion = "1.0";
    std::string sourceDocumentName = "database_snapshot";
    bool includeRawSqlDescriptions = true;
    bool includeIndexes = true;
    bool includeViews = true;
    bool includeTriggers = true;
};
```

## Source metadata

Exported documents are marked as database exports:

```cpp
SchemaDocumentSourceType::DatabaseExport
```

This is important because uploaded user XML and database-exported XML are different artifacts:

```text
uploaded XML schema       user intent / desired model
exported DB schema        current database state
```

A database export must not overwrite the user's uploaded XML schema.

## Mapping rules

### Tables

Every database table becomes one `EntityDefinition`.

```text
DbTable -> EntityDefinition
```

The original table name is preserved in:

```cpp
EntityDefinition::tableName
```

A stable entity name is generated from the table name, for example:

```text
products        -> Products
order_items     -> OrderItems
```

### Columns

Every non-FK column becomes a `FieldDefinition`.

```text
DbColumn -> FieldDefinition
```

Basic metadata is preserved:

- name;
- type;
- nullable;
- primary key;
- unique;
- default value;
- collation;
- computed expression;
- autoincrement flag.

### Foreign keys

Columns that appear in `DbForeignKey` become `ForeignKeyField` entries instead of regular `Field` entries.

```text
DbColumn + DbForeignKey -> ForeignKeyField
```

The reference target is preserved as:

```cpp
ForeignKeyField::references
ForeignKeyField::toField
ForeignKeyField::onDelete
ForeignKeyField::onUpdate
```

### Indexes

Explicit indexes become `IndexDefinition` entries.

SQLite internal auto-indexes are filtered earlier by `DatabaseIntrospector` and should not appear as user-visible indexes.

### Views and triggers

Views and triggers are exported when enabled in `DatabaseSchemaExportOptions`.

Some trigger metadata may be incomplete depending on the database driver. If the exporter cannot map a trigger event/timing to values supported by `schema_app.xsd`, it emits a warning and uses a conservative XSD-compatible fallback.

## Type mapping

The exporter maps driver-specific database types to values allowed by `schema_app.xsd`.

Examples:

```text
INT                  -> INTEGER
CHARACTER VARYING    -> VARCHAR
NUMERIC              -> DECIMAL
BOOL                 -> BOOLEAN
TIMESTAMPTZ          -> TIMESTAMP
CLOB                 -> TEXT
```

Unsupported types are exported as `TEXT` and produce warnings.

This is intentional: exported XML must stay compatible with the XSD contract. More precise driver-specific type handling belongs to `DriverCapabilities` and diff/planner work.

## Validation

The canonical XML generated by `SchemaDocument::toCanonicalXml()` should validate against:

```text
qornix_orm/schema/schema_app.xsd
```

When `libxml2` support is enabled, `database_schema_exporter_test` validates the exported XML string against the XSD.

## Current limitations

The exporter provides the database-to-schema export layer. It does not implement semantic diff.

Known limitations:

- PostgreSQL/MySQL typed introspection is still shallow if the driver returns only table/column names;
- some raw database types may be exported as `TEXT` with a warning;
- trigger event/timing extraction depends on driver metadata quality;
- constraints are exported only when present in `DatabaseSnapshot`;
- destructive schema decisions are not made here.
